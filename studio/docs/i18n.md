# 多语言组件

模板默认支持英语、西班牙语、法语、德语、葡萄牙语、意大利语、日语、韩语和中文，首次访问固定使用英语，不读取浏览器语言。用户主动切换后，语言值会写入项目独立的 localStorage 键。

## 文件职责

| 文件 | 职责 |
|---|---|
| src/i18n/config.ts | 支持语言、显示名称、HTML 语言值和 Intl 区域 |
| src/i18n/messages.ts | 类型安全的界面翻译字典 |
| src/i18n/I18nProvider.tsx | 当前语言、持久化、数字与金额格式化 |
| src/i18n/useDocumentMetadata.ts | 页面标题、描述和 Open Graph 元数据同步 |
| src/i18n/utils.ts | 字符串插值和 API 错误码翻译 |
| src/components/LanguageSwitcher.tsx | 可在任意页面复用的语言选择器 |

## 页面中使用

    const { locale, messages, setLocale, formatNumber, formatCurrency } = useI18n();

页面只读取 messages，不直接判断语言。动态值使用 interpolate：

    interpolate(messages.projects.open, { name: project.name })

## 增加语言

1. 在 LOCALES 中增加语言代码
2. 补充 LOCALE_LABELS、HTML_LANGS 和 INTL_LOCALES
3. 在 MESSAGES 中补充完整字典
4. 运行 npm run check 和 npm test

Messages 接口与测试会阻止某种语言遗漏字段。

## 裁剪语言

九种语言是类型和测试共同强制的：Messages 接口要求每种语言字段齐全，i18n 测试会比对九种语言的结构完全一致，邮件测试会比对九种语言的模板集合完全一致。这在维护完整产品时是保障，在只面向一两个市场时就是负担。

只保留中文和英文的做法：

1. 把 src/i18n/config.ts 的 LOCALES 改成 ["en", "zh"]
2. 删掉 LOCALE_LABELS、HTML_LANGS、INTL_LOCALES 中多余的条目
3. 删掉 src/i18n/messages.ts 的 MESSAGES 里多余的语言块
4. 删掉 src/lib/email/templates.ts 里多余的语言常量，并同步收窄 EMAIL_COPY
5. 改掉 src/i18n/i18n.test.ts 里针对具体语言的两条断言
6. 运行 npm run check 和 npm test

改第一步之后 npm run check 会精确列出剩下五处：config.ts 的三张映射表、messages.ts 的 MESSAGES、templates.ts 的 EMAIL_COPY 和 i18n 测试里的语言断言，照着修即可，不需要手工搜索引用。DEFAULT_LOCALE 必须仍在 LOCALES 之内，它同时是界面兜底语言和邮件兜底语言。

反过来增加语言时，第四步同样不能漏：界面翻译齐全但邮件模板缺失，会在发信时静默回落到英语。

## API 错误

界面不依赖服务端英文错误文案，而是根据稳定 code 翻译。新增写接口时应返回类似结构：

    { "code": "invalid_project_url", "error": "Invalid project URL." }

code 供界面翻译，error 供日志和没有对应翻译的客户端诊断。业务枚举值、数据库分类和支付提供商名称保持规范值，只翻译展示标签。

## 边界

模板只提供通用界面字典。服务条款、隐私政策、退款政策、支付说明和领域规则必须按实际项目、商品与司法辖区重新编写，不能把其他项目的内容直接复制到新项目。
